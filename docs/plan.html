01What version 1 is

The definition of done, in one paragraph, and the scope lines around it.

v1

A stranger can install the app from a store, create an account, answer the onboarding questions, get a plan that respects their schedule and fitness, see today's workout, log runs in seconds, give feedback, watch the plan adapt with a stated reason, manage or pause the plan, see their progress, and delete their account. The server survives a provider outage, a double-submitted log, and a bad LLM proposal without corrupting anyone's plan.

In

  • Accounts, onboarding, feasibility
  • LLM plan generation with Java validation
  • Today, week, workout detail, logging, feedback
  • Adaptive coaching with reasons and undo
  • Progress, records, manage plan
  • Account deletion with a 14-day window

Behind a flag

  • Health Connect and HealthKit import of runs recorded by watches and other apps
  • Built in the app phase, shipped on if stable, otherwise a 1.1 update
  • Manual logging is always the base path

Out

  • GPS tracking in the app, guided audio, race recommendations, social
  • Social sign-in, Keycloak, Kubernetes
  • Second LLM provider
  • Config server and service discovery as requirements

03Principles that decide the small cases

When a question comes up that this document does not answer, one of these usually does.

The client expresses intent; the server decides.

A flag like "accepted compressed plan" is the user saying "I understand". The server recomputes the verdict and only honours the flag if its own answer makes it meaningful.

LLM output is untrusted input.

Same category as a form from a stranger: parsed, validated against the rules, rejected if bad. The LLM never decides whether a plan is accepted.

Whoever decides also explains.

The server returns the verdict, the inputs it used and the allowed actions. The app renders what it receives and never composes its own reasons.

Nothing changes silently, nothing is deleted.

Every plan change is a revision with a reason. Undo is a compensating revision. Completed workouts are never touched.

Never block logging.

A runner can always record a run, even while a job is in flight. Jobs apply with a compare step and conflict rather than corrupt.

Measured versus estimated, always labelled.

Typed distance and time are measured. Anything derived is estimated. The server labels; the app shows the label.

Rest is a workout; missed is not failed.

Rest days get full rows and a reason. Missed workouts are neutral and absorbed, never stacked onto the next session.

Repeatable by design before idempotency keys.

Logging is "set the result of workout 42", so retries are harmless. Keys only where an overwrite is impossible, such as generation.

Whoever creates a thing picks its ID.

The server creates plans and workouts. The app creates free runs, so it generates their UUIDs. Ownership is checked regardless.

04Architecture

Four Spring Boot services behind one gateway, one MySQL server with a schema per service, RabbitMQ for events. Microservices from the start was Yogesh's call, made knowing it costs two to three extra months and about 40 dollars a month more than a monolith.

Identity

Owns users, credentials, refresh tokens, verification and reset tokens

Hand-built JWT access tokens of about 15 minutes and database-stored refresh tokens of about 30 days, rotated and revocable. Keycloak replaces it in version 2.

Training

Owns profile, goal, plan, weeks, workouts, results, feedback, revisions, rules

The whole domain, kept together because workouts, results and revisions need transactions with each other. Splitting it would create the distributed-consistency mess the course warns about.

Coach

Owns prompts, provider adapter, proposal records, LLM log, limits, cache

Deliberately dumb: take a request, build a prompt, call the provider, return a proposal. No domain tables, ever. If it starts wanting plan tables, the boundary is drifting.

Notification

Owns outbound messages and delivery state

Consumes events and sends email now, push later. The simplest service, so it is where messaging is learned first.

Infrastructure choices

  • Spring Cloud Gateway as the only public entry point. Token validation is one replaceable piece so Keycloak can slot in later.
  • RabbitMQ through Spring Cloud Stream, so a later swap to Kafka is mostly configuration. Outbox on every publisher, idempotent consumers, dead-letter queue.
  • Resilience4j on every service-to-service and provider call: timeouts, retries with backoff, circuit breakers.
  • OpenTelemetry and Grafana for logs, metrics and traces, with a request ID that crosses the broker. The stack runs on a laptop until launch.
  • Environment variables and Compose service names for config and discovery in version 1. Spring Cloud Config and Eureka are optional learning add-ons.
rc

Order of birth: identity alone behind the gateway, then training trusting the token, then the broker with notification as the first consumer, then coach with the outbox and the generation saga. One distributed-systems concept per step.

05Plan generation, end to end

The one workflow that touches every piece. Each step is a boundary where something can fail, and each has a rule for what happens when it does.

App
Submits onboarding. One request, complete answers.
Training
Validates answers, re-runs feasibility, saves profile and goal, writes a generation request plus an outbox row in one transaction.
Outbox relay
Publishes "generate plan" to RabbitMQ. One in-flight job per user; a retry returns the existing job.
Coach
Checks limits and cache, builds the versioned prompt, calls Anthropic with structured output, logs tokens and latency.
Training
Validates the proposal against the rules. On violations, one repair round with the violations fed back.
Outcome
Accepted: expanded into weeks and workouts with IDs, cached by input hash. Failed twice: honest "try again later"; answers are kept.

The app polls a status endpoint while the job runs and shows a "building your plan" state. Nothing in the app is blocked by the job except the plan itself.

06Decisions by topic

Each with its reasoning in a line. Ember marks a decision Yogesh made against the initial recommendation.

Accounts

5
Email and password, hand-built with Spring Security.
To learn token mechanics properly. Social login and Keycloak are version 2.
Short access token plus revocable refresh token.
Stateless tokens cannot be revoked; the refresh token in the database makes sign-out-everywhere and deletion real.
Every user-owned row carries the user ID; no endpoint takes one from the client.
Ownership is a habit, tested on every endpoint.
Verification before plan generation; single-use expiring reset links.
Generation costs money. Email provider chosen at phase 7.
Deletion: 14-day deactivation window, then purge.
A saga: identity marks and publishes, training and coach purge and confirm, identity hard-deletes. Anonymised aggregates kept.

Onboarding and profile

6
One request at the end; the app holds a draft.
The server only ever sees complete profiles.
Server re-validates every answer.
Old app versions and other clients send old shapes.
Profile and goal are separate entities.
They change for different reasons; a plan is generated from the pair.
Metres and seconds, integers, everywhere.
Clients format. Avoids a class of rounding bugs.
Injury data is structured fields only.
Free text invites medical history we would be responsible for.
Editing an answer during an active plan is a plan operation.
Old answers are kept so a revision can cite "profile version 3".

Goal and feasibility

4
Separate feasibility endpoint, re-run inside generation.
Good screen experience; the server never builds a plan for an unverified goal.
Verdict carries weeks, minimum and typical, inputs used, allowed actions, wording.
The app renders; it does not compose.
Rules table is versioned; every plan records its version.
Tightening a rule never invalidates old plans.
Claude seeds the rules table at phase 2; Yogesh owns it.

Plan generation

7
The LLM generates the whole plan; Java validates; no template fallback. Yogesh's call
More varied, coach-like plans; a fallback is double work and undercuts the AI-coach promise. On failure the user keeps their answers and retries.
One repair round, then honest failure.
A high failure rate means the prompt is wrong, not the validator.
Anthropic only, behind a port for a later second adapter.
Background job, status endpoint, one in-flight job per user.
Whole-plan generation takes tens of seconds.
Accepted plans cached by hash of inputs, rules and prompt versions.
Reproducibility from the database, not the model.
5 generations per user per day, shown in the app; 5 adaptations a week; global token budget with alert and hard stop.
LLM contract drafted at the start of phase 3.
JSON schema, validator rule list, repair format, prompt versioning.

Scheduling

6
Workouts are rows with a local calendar date; the profile stores the time zone.
"Today" is the user's date. Event timestamps are UTC.
Missed is marked lazily on app open; scheduler in version 2.
Statuses: scheduled, completed, partial, missed, skipped, moved.
Skipped is a signal, missed is an absence, partial is below the completion threshold.
Reschedule within the week only, from server-provided days; no version bump.
Hard days 48 hours apart, never onto the long-run day or into the past.
Cross-week moves go through the revision engine with confirmation.
Never a load increase as a side effect. Importance rank decides what is dropped.
Optimistic locking per workout and per plan.
Two devices, two taps: a stale update conflicts.

Logging and feedback

5
One request, prefilled; Done works without touching anything.
Planned targets stay on the workout; actuals live on the result row.
Set-by-overwrite per workout; free runs carry an app-generated UUID.
Retries are harmless. Events only on real change.
Edits any time, deletes allowed; past adaptations not unwound.
Untouched defaults saved but flagged as defaulted.
The engine weighs deliberate answers more.
Health import proposes, user confirms; manual is the base path.
Completion threshold about 90 percent. Result rows carry source and external ID.

Adaptive coaching

6
Two stages: Java decides whether and in what scope; the LLM proposes inside that scope.
The safety decision is testable Java.
All eight reason codes in version 1; thresholds in the rules table.
Pain outranks everything. Suppressed rules are logged.
Easing auto-applies with undo; increases and restructures ask.
Pain never leads to an increase; repeated pain pauses hard sessions.
Runs right after the signal; at most one feedback-driven revision a day.
Runner self-adjustments are deterministic Java, no LLM.
"Not feeling well" never yields an easier workout; it skips and routes to the pause or pain path.
Every change is a revision; undo compensates; apply with compare-and-apply.

Progress and records

3
Computed on read; no precomputed summaries.
Milliseconds over a few hundred rows; precomputation drifts on edits.
Records within about 2 percent of a standard distance, labelled with source.
Best efforts shown separately.
Skips honour consistency, misses break it. No projected finish times.

Managing the plan

4
One active plan per user; states active, paused, ended, completed; everything kept.
Restart is a new plan; goal or schedule changes regenerate ahead only, with confirmation.
Server-enforced guards on every transition; nothing changes while a job is in flight.
Race result recorded as the outcome, prefilled from a synced run, confirmed by the runner.
Watch time and chip time differ.

Cross-cutting

3
API versioning by path, additive only; app build number in a header.
Coach sentences are server-generated from reason codes and templates.
Testable, and never says what the rules did not decide.
Store and legal checklist at phase 8.
Written from what the system does, so after it exists.

10Phase 1, the first ten sessions

Each is 30 to 45 minutes with a verifiable outcome. Yogesh writes the code; Claude reviews. The question at the end of each is the interview rehearsal.

01
Repository and the identity skeleton
Create the runcoach repo with a folder per service and an infra/ folder. Generate identity-service from Spring Initializr: Boot 3.5.x, Java 21, Web, Data JPA, MySQL Driver, Flyway, Validation, Actuator, Security, Docker Compose Support, Testcontainers. Boot it against Dockerised MySQL; health is UP.
Explain: why Flyway instead of Hibernate creating tables.
02
First migration and entity
Flyway migration for users: id, email unique, password hash, status, time zone, created at. User entity and repository. One Testcontainers test that boots the context and proves the migration applied.
Explain: what the persistence context is and when an entity becomes managed.
03
Registration endpoint
POST /v1/auth/register with a request DTO, Bean Validation, BCrypt hashing, 201 on success, 409 on duplicate email. Integration tests for both.
Explain: why the DTO is not the entity.
04
Error format and request IDs
Global exception handler producing RFC 9457 problem details for validation, conflicts and unknown errors. A filter that assigns a request ID and logs it on every line.
Explain: why clients need one error shape.
05
Spring Security, stateless
Security filter chain: register and login open, everything else denied, no sessions. POST /v1/auth/login issues a signed JWT access token with a 15 minute expiry.
Explain: what the filter chain is and in what order filters run.
06
Verifying tokens and the current user
A JWT filter that authenticates requests; GET /v1/me; the current-user resolution every later endpoint reuses. Tests for 401 without a token, 401 expired, 200 valid.
Explain: what is inside a JWT and why the server can trust it without a database lookup.
07
Refresh tokens
Refresh token table, rotation on use, reuse detection that revokes the family, sign-out and sign-out-everywhere. Tests for the replay case.
Explain: why refresh tokens live in the database when access tokens do not.
08
The gateway
Spring Cloud Gateway project routing /v1/auth/** and /v1/me to identity, validating the access token at the edge with the public key. Docker Compose for gateway, identity and MySQL together.
Explain: what the gateway must never do.
09
CI
GitHub Actions: build both services, run tests with a MySQL container, build and push Docker images on main. Green main is the only thing that deploys.
Explain: why the test database is a real MySQL, not an in-memory substitute.
10
Rate limiting and the phase review
In-memory rate limits on register and login at the gateway. The account deactivated state and the deletion request stub. Update this document with what changed.
Explain: the three things a backend must do before it trusts a request.

13Concepts you should be able to explain

Each came up as a design decision. Explaining the decision and the alternative you rejected is the interview value of this project.

Determinism

Same input, same output. Lost in the LLM, recovered in the validator and the input-hash cache.

Idempotency

Doing it twice has the same effect as once. Achieved by design (PUT overwrite) before reaching for keys.

Optimistic locking

A version number on the row; a stale update is rejected rather than overwriting.

Snapshot, work, compare-and-apply

Read a version, do slow work outside any transaction, apply in a short transaction that re-checks the version.

Outbox pattern

Write the event with the data in one transaction; a relay publishes it. No lost or phantom events.

Saga

A workflow across services with compensation instead of a shared transaction. Generation and deletion are the two in version 1.

Transaction boundary

Wrap the save, never the network call. A transaction holds a connection; a 20 second LLM call inside one drains the pool.

Database per service

Schemas owned by one service each, no cross-schema queries. Data ownership is what makes boundaries real.

Boundary by operational profile

Coach is separate because its latency, failure modes, cost, secrets and scaling differ, not because the LLM is special.

Rule versioning

Every plan records the rules version that built it, so tightening a rule never invalidates old plans.

Time zones

Calendar dates for workouts in the user's zone; UTC timestamps for events. "Today" is computed per user.

Client intent, server decision

Flags express what the user wants; the server recomputes what is allowed. The compressed-plan flag is the worked example.
